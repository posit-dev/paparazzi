## Problem and empirical evidence

The Actions paragraph in `.agents/SPEC.md` makes navigation after actions an explicit `pz_wait_for_navigation()` call; the Waits API index confirms its shape. `action_start()` (`R/actions.R`) records the beginning of an action; `nav_snapshot()` and `nav_settle()` (`R/wait.R`) compare `performance.timeOrigin` at wait start, after settling, and against that action start. A bfcache restore retains the old document and its old time origin. If the restore completes before the wait, all three values fail to demonstrate a navigation, despite the restored document being different from the one the action left. `wait_nav_reset()` consumes the action evidence after success. Existing fast-link tests in `tests/testthat/test-wait.R` exercise new documents but not bfcache.

Scratch probes (scripts `/tmp/xwzz-bfcache-probe.R`, `/tmp/xwzz-bfcache-http-probe.R`, `/tmp/xwzz-bfcache-loader-probe.R`; outputs `/tmp/xwzz-bfcache-probe.log`, `/tmp/xwzz-bfcache-http.log`, `/tmp/xwzz-bfcache-loader.log`) used package `pz_open()` and `pz_click()` with Chrome/153.0.8010.53, through `/tmp/pz-chrome-lock.sh`. On `file://` (the current nav fixtures), Chrome did **not** restore from bfcache: `Page.backForwardCacheNotUsed` reported `SchemeNotHTTPOrHTTPS` and `BrowsingInstanceNotSwapped`; returning A got a new `timeOrigin`, new JS marker, `pageshow(false)`, and `Page.frameNavigated` with `type = "Navigation"`. On an HTTP server at `127.0.0.1`, clicking A → B then the button calling `history.back()` on B **did** restore from bfcache: A retained its original time origin (`1790379932558` in the probe), JS marker, and `performance` navigation entry `type = "navigate"`; `pageshow` changed from `[false]` to `[false,true]`. CDP emitted `Page.frameNavigated` for the restored main frame with `type = "BackForwardCacheRestore"` and A's original `loaderId`. It also emitted `frameStartedLoading`/`frameStoppedLoading` (order of observed callbacks: started, stopped, frameNavigated on restore); no `navigatedWithinDocument` or `lifecycleEvent` was observed. `Page.getFrameTree()` reported A's original loader ID again after restore, differing from B's loader ID. These observations mean a `file://` regression alone cannot reproduce this bug.

## Proposed mechanism

Use synchronous CDP document identity, without injecting a script or subscribing to a page-lifetime event. In `action_start()` (`R/actions.R`), capture `Page.getFrameTree()$frameTree$frame$loaderId` **before** the action's first browser interaction, then record the existing epoch-ms action start (after that CDP response). Store those two pieces together as the existing `PaparazziPage` (`R/context.R`) `last_action_start_` evidence, updating its comment and the `nav_settle()` caller; do not add a second ordering flag. A cached A document's loader ID is restored unchanged, while the B document that the button acted on has another loader ID (confirmed in the HTTP probe). In `nav_settle()` (`R/wait.R`), keep the current wait-start and time-origin evidence and complete-and-stable hold. If there was a last action, and both loader IDs are non-null, a differing *main-frame* loader ID from `Page.getFrameTree()` is additional evidence that the settled document is not the document where that action started, even if its `timeOrigin` is older. Read the settled loader ID only when the existing 0.5-second hold has elapsed and the origin-based evidence does not already suffice; do not make every poll depend on another CDP request. If the document changes during the identity read, retry until the page is stable; no additional poll timer is needed. `wait_nav_reset()` already clears the action evidence on success or `wait = "none"`. Keep `paparazzi_error_timeout` and its existing `Timed out after ... waiting for the navigation to complete.` message for a non-navigation. No new input or error class.

The added synchronous CDP round trip on **every user action** is the tradeoff of this design. An action that fails to resolve still pays for identity capture, as it already records action start before resolution. If an action is issued on a temporarily missing frame, follow the project's existing browser-error behavior rather than disguising an inability to establish its identity as positive navigation evidence. Orchestrator: confirm this latency cost is acceptable before stage 2.

Alternatives: `Page.frameNavigated(type = "BackForwardCacheRestore")` does fire on HTTP bfcache restoration, but the event has no timestamp: a callback queued before a later non-navigating action and delivered after its `action_start()` can be misattributed. Avoid a page-lifetime listener, callback bookkeeping, or a new ordering flag just to resolve this race. `pageshow(persisted)` needs a listener already installed in the earlier document (new-document init script / init-restore window **tripwire: stop and seek sign-off, not this phase**); `performance.getEntriesByType('navigation')[0].type` stays `navigate` on the cached original document; the existing time-origin comparison fails by definition; URL comparison cannot detect same-URL history entries or reloads; `frameStoppedLoading` is not specific to bfcache. No timers, queues, second ordering flags, or display-shaped state are proposed. If a reliable solution requires one, stop and report options to the orchestrator rather than building it.
