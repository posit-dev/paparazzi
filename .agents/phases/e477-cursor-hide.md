## Conclusion and signed-off disposition

**Case (c): neither the historical walkthrough chain at 6fccf5a nor the same chain on main reproduces an overlay reappearing during typing.** The original sampled video frames likely showed the I-beam *after* the explicit `pz_cursor_show()` while the fully typed text remained in the field (the shown overlay is captured in frame 33/35 of the instrumented runs). The native input caret may also be visible while typing, but it is a separate, narrow stroke at the text insertion position, not the overlay's fixed I-beam. A hide-fade overlap is inconsistent with the computed-opacity-at-input log. `stage_move_cursor()` returns early when `cursor_visible()` is false; explicit hide changes that visibility to `hidden` in both versions. The later cursor-rest commits 177f263 / 09d6bef do not fix this supposed hide-then-type defect: 6fccf5a already meets the contract.

Stage 2 adds **only** a cheap DOM-level regression test to `tests/testthat/test-cursor.R`: on the tasks page, record a click, explicit hide and targeted typing of `abc`; a page-side input listener captures computed overlay opacity on each of three input events. The test checks three events, all zero opacity, R cursor visibility still `hidden`, and explicit show restores visibility. There is no pixel-ROI test and no production change.

Discrimination: temporarily removed the hidden-cursor early return in `stage_move_cursor()` so the targeted typing path drew the cursor; the cursor test suite reported **FAIL 1 / WARN 0 / SKIP 0 / PASS 459** (the new per-input opacity assertion failed). Restored `R/stage.R`; rerun reported **FAIL 0 / WARN 0 / SKIP 0 / PASS 460**. `air format --check .` and `jarl check .` pass. All browser runs used `.agents/chrome-lock.sh`.
